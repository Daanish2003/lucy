Always-on architecture

A one-page summary of Lee Robinson's “How always-on agents work” (Stanford CS146S, Oct 2026). All numbers are the lecture's, not general rules.

Week-one agent → always-on agent

Week-one agentAlways-on agent
Runs in your terminalRuns on a server: survives crashes, deploys, a closed laptop
Uses your laptopOwn cloud computer (VM with desktop, browser, files)
Remembers only messagesSaves state, memory and skills; summarizes old messages
Prints every replySpeaks only through a send tool, so it can stay quiet
Starts when you typeStarts on events: messages, schedules, Slack, calls, finished work
One task, then exitsWorks for months, same memory, many conversations

Lifecycle

Trigger → router (dedupe, pick conversation, record source) → per-conversation queue (one turn at a time) → turn (load state, model ↔ tools, save every step) → anything worth saying? (send tool, or stay quiet) → idle ~2 min → process stops.

The computer is restored only when a tool needs it. It sleeps a few minutes after the last activity, never mid-turn: files sync, then a snapshot is taken, then it stops. Saved state lives in the server database.

When nothing is happening, nothing runs. Everything that matters is saved, so any trigger can bring it back.

Choosing a wake mechanism (Lesson 2)

  1. Source can push? → event. One session per event, untrusted payload, dedupe on the provider's event ID, flood guard and batching.
  2. Trigger is a time, or a source you have to poll? → schedule. Saved prompt, user-approved. Dedupe on routineId:scheduledFor. Run at :07, not :00.
  3. Only an open-ended “anything need me?” left? → heartbeat. Keep it narrow, isolated session, active hours only, NO_REPLY by default. Costs money on every tick.

Products' limits: Grok Bot routines ≥ 5 min apart (≤ 50 per Bot). Claude routines ≥ 1 h. OpenClaw heartbeat 30 min by default; event turns ≥ 30 s apart, flood guard after 5 in 60 s.

Message sync

  • Client shows the message immediately and assigns a unique ID. The server drops IDs it has already seen, so retries are safe.
  • Server broadcasts a data-less “something changed” signal, and apps fetch from the DB. A lost signal is harmless.
  • Updates carry sequence numbers. When there's a gap, the app reloads from the DB.
  • The owner's 1:1 messages and Stop skip the queue and interrupt the turn. Everything else waits in FIFO order, and quick bursts are batched into one turn.
  • Queue modes (OpenClaw): collect (merge into one follow-up turn, 500 ms debounce) · followup (one turn each) · steer (inject at the next model boundary and skip unstarted tool calls; OpenClaw's default) · interrupt (abort, then run the newest).
  • Abort ≠ start now. Wait for the aborted turn to settle before the next one starts. This is safe because every step was saved. (Exercise: build/01-router.)

Harness

  • SendToUser is the only way to talk to the user. Thinking stays private and silence is allowed. The last send can end the turn without another model call.
  • Purpose-built approval UIs: password autofill that the model never sees, Allow/Deny cards for payments, full email drafts, reactions.
  • Tool schemas on demand: tool names go in the prompt up front, and details load when needed.
  • Cheapest first: what it already knows → connector API → web search → its signed-in browser → full desktop → ask you. If a connector is broken, ask rather than work around it.
  • Main agent + helpers: each helper gets a full task description and a fresh context, and returns a short report.
  • Tool tips: keep the tool set stable (unavailable tools return an error), keep each description and schema under 4,000 characters, use a dedicated tool to save state, and write errors that say what to do next.
  • Safety: a separate model reviews risky actions (no answer in 15 s means blocked). Email and webhook text is labelled untrusted. Memories are information, not instructions. It asks before messaging people or creating routines. Secrets go in env vars.

Context engineering

  • Stable prefix (tools, system prompt with a memory snapshot, first message), then an append-only history, then the newest message (time, what changed, the message itself). This keeps the provider cache warm.
  • Treat a cache miss like a bug: fixed sorted order, each section hashed, tool changes sent as notes, and the cache warmed when the user opens the chat.
  • Keep the main context small: outputs go to files, screenshots and heavy tool work go to helpers, instructions become skills.
  • Summarize while idle: about 10 minutes after a turn over 100k tokens, while the cache is still warm. Keep the last few sent messages word for word.
  • Memory tiers: profile (always in the prompt, ≤100 facts / 4,000 characters) → log (top 30 recent entries) → notes (fade) → search.
