**What the talk covers (secondary, from Wallstreetcn's summary; check against the video):**
- The main example is Grok Bot: a thin client with a fixed server-side agent, plus plugins, cron-style routines and skills.
- The agent runs on its own cloud Linux machine. It sleeps until a trigger (Slack, email, other events) wakes it. State is saved to a database, and the VM is paused or snapshotted to save cost. Firecracker VMs are mentioned.
- A router deduplicates incoming events and decides whether an update is worth interrupting the user for. The user's own messages take priority; everything else is queued and batched.
- Durable workflows (Temporal) resume from the failed step.
- Sub-agents get fresh context.
- Tools are discovered dynamically and escalated from cheapest to most expensive: conversation history, then plugins/MCP/APIs, then web search, then browser, then full desktop, then asking the human.
- Prompt caching: "a cache miss is treated as a bug." The talk cites OpenClaw's early-2026 cache-miss problems.
- Memory is layered, and skills are Markdown files.
- An "auto-review" model approves actions in place of a human.
- An eval flywheel turns failures into evals.
- Predictions: agents running continuously for weeks or months within 6–12 months, and every product needing an agent interface or ending up as "headless data" for other agents.

## 2. What "grok bot" and "OpenAI dots" are

### "Grok bot" = **Grok Bot** from xAI (launched 2026-08-11), not just the @grok reply bot
- **What it is:** xAI calls it "a team of always-on AI agents." Each has its own computer, works inside your tools and apps, and only checks back when something needs approval. It was released in beta on 2026-08-11. https://x.ai/news/introducing-grok-bot
- **Runtime:** Every Bot works on a persistent cloud computer with a browser, filesystem and terminal. All Bots on one account share the same machine, so cookies, files and CLI credentials are shared too. Each Bot's screen is a separate work surface, but it is not a security boundary. https://docs.x.ai/grok-bot/overview (via search extract), https://docs.x.ai/grok-bot/computer-and-apps
- **Triggers:**
  - Routines run on a schedule (at least 5 minutes apart), or start from Cursor account-integration events such as a Slack message or GitHub notification.
  - Each Bot can own up to 50 routines.
  - Skills are saved instructions, and a Bot can learn one from a demonstration of up to 10 minutes.
  - Routines keep running when your laptop is closed.

  https://docs.x.ai/grok-bot/skills-routines-and-automations
- **Safety:**
  - Approvals offer "Allow once / Always allow / Deny."
  - **Auto Review** is a separate layer that checks shell commands, plugin calls, computer use and delegation.
  - Bots have no credentials of their own. Connector tokens stay on Cursor's backend.
  - Untrusted content is labeled as untrusted. The docs admit these controls "reduce, but do not eliminate, risk."

  https://docs.x.ai/grok-bot/security
- **Infrastructure:** It runs on Cursor-hosted cloud computers, and enterprise users each get a Firecracker microVM. https://docs.x.ai/grok-bot/security, https://docs.x.ai/grok-bot/teams-and-enterprises (via search extract)
- **On X:** Tagging **@bot** in a post on X hands that post to your own Grok Bot as a task. This is separate from the older **@grok** reply bot, which just answers in the thread; if a post tags both, @bot stays quiet. https://docs.x.ai/grok-bot/tag-on-x
- **Why it matters here:** Robinson's own post says "always-on, proactive agents like @Bot," and the talk uses Grok Bot as its main case study. https://digg.com/ai/vra86c5o, https://wallstreetcn.com/articles/3783496

**Conclusion:** "grok bot" means xAI's Grok Bot product. The @grok reply bot on X is a less likely reading, because it is reactive: it only replies when tagged. That makes it a counter-example of an always-on agent.

### "OpenAI dots" = **dots**, a real OpenAI product (DevDay, 2026-09-29). It is not a mishearing.
- OpenAI's "Introducing dots" page calls them "remarkably capable, always-on agents built to handle everything." They run on GPT-6 Astra, each has its own cloud computer, and they connect to 4,000+ apps through plugins. You reach them in ChatGPT (desktop, web, mobile), Slack and Teams. They are rolling out to Pro, Business Premium and Enterprise. https://openai.com/index/introducing-dots/ (via search extract; 403 to the fetcher)
- If the monitoring system detects a safety concern, it "can pause or stop the dot's work." OpenAI also tells users to "always review consequential work." Same source.
- Proactive searches in connected apps are read-only. Users choose which actions run on their own and which need approval. Pro access excludes the EEA, Switzerland and the UK. https://www.ilfoglio.it/en/foglio-ai/2026/10/10/news/what-are-always-on-agents-which-continue-to-run-after-youve-switched-off-your-computer--409720 (secondary), https://help.openai.com/en/articles/20001530-getting-started-with-your-dot (via search extract)
- TechCrunch adds that you can launch dots from Codex or ChatGPT. Dots can be given their own identities and credentials, and an integration with Microsoft Agent 365 security controls is in progress. https://techcrunch.com/2026/09/29/openai-launches-dots-its-bubbly-agentic-avatar/
- **Earlier OpenAI product:** ChatGPT **Pulse** (Sept 2025) researched proactively overnight and delivered results once a day. It was sunset in June 2026 as "proactive updates move into scheduled tasks." https://openai.com/index/introducing-chatgpt-pulse/, https://help.openai.com/en/articles/6825453-chatgpt-release-notes (via search extract)

**Other candidates I considered and rejected:** Pulse (sunset), ChatGPT Tasks/scheduled tasks (a simpler scheduler), and an always-on device. With a product literally named "dots" launched three weeks ago, the match is unambiguous.

## 4. Engineering concepts

**Event triggers vs. chat triggers (the "ambient" idea).**
An ambient agent "listen[s] to an event stream and act[s] on it accordingly, potentially acting on multiple events at a time." It isn't started only by a person sending a chat message. In practice, triggers are webhooks (GitHub PR events, Slack messages), app events, and inbound messages, and each matching event usually starts a new session.
Sources: https://www.langchain.com/blog/introducing-ambient-agents , https://code.claude.com/docs/en/routines

**Schedulers / cron.**
Time-based triggers run a saved prompt with its context on a cadence. Products put floors on them: Grok Bot needs routines at least 5 minutes apart, and Claude routines at least 1 hour apart. They also cap how many runs you get, which is mainly cost and abuse control. Expect jitter: Anthropic suggests scheduling at odd minutes like 9:07 because runs can start a few minutes late.
Sources: https://docs.x.ai/grok-bot/skills-routines-and-automations , https://code.claude.com/docs/en/routines

**Heartbeats.**
A heartbeat wakes the agent at a fixed interval in its *main* session to work through a natural-language checklist (HEARTBEAT.md). If nothing needs attention, the agent replies with a silent token (HEARTBEAT_OK) that the system swallows. OpenClaw's guidance is to use cron for exact timing or isolated runs, and heartbeats for batching checks that can drift a bit and benefit from conversation context. Heartbeats are now implemented as system-owned cron jobs.
Sources: https://docs.openclaw.ai/gateway/heartbeat , https://github.com/openclaw/openclaw/pull/112585 , https://github.com/openclaw/openclaw/issues/53252

**Long-running loops across context windows (the harness).**
Each new session "begins with no memory of what came before." Anthropic's fix:
- An initializer agent writes an init script, a progress log, a JSON feature list (all marked failing at first), and a first git commit.
- Each later session reads those, does one feature, and leaves the code clean.

The point is for a fresh context to "quickly understand the state of work."
Source: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

**Durable execution / crash recovery.**
Keep the agent loop stateless and store progress outside it, so a crash resumes instead of restarting. Two approaches:
- Anthropic's Managed Agents splits the agent into session (an append-only event log), harness (the loop) and sandbox (the "hands"). After a crash, `wake(sessionId)` and `getSession(id)` replay from the last event.
- Temporal models the loop as a Workflow, with each LLM or tool call as an Activity, so the loop resumes after failure. It also has patterns for approvals and long waits.

Sources: https://www.anthropic.com/engineering/managed-agents , https://docs.temporal.io/ai , https://temporal.io/blog/temporal-agent-harness-durable-agent-infrastructure

**Checkpoints and human-in-the-loop interrupts.**
In LangGraph, `interrupt()` pauses the graph, saves state through a checkpointer, and waits indefinitely until someone resumes it with a `Command`. That is how an agent can wait days for an approval without holding a process open. Use a durable checkpointer in production. Because a node re-runs from its start on resume, don't loop `interrupt()` inside a single node.
Sources: https://docs.langchain.com/oss/python/langgraph/interrupts , https://docs.langchain.com/oss/python/langgraph/checkpointers

**Inbox / notification UX.**
LangChain names three human-in-the-loop moves: **notify** (flag it, don't act), **question** (ask for missing information), and **review** (approve, edit or give feedback on a proposed action). They tried Slack first, but notifications got lost, so they built an "Agent Inbox" modeled on an email inbox crossed with a support-ticket queue. Robinson's talk adds a router that dedups and batches events and decides what deserves an interruption (secondary source).
Sources: https://www.langchain.com/blog/introducing-ambient-agents , https://github.com/langchain-ai/agent-inbox , https://wallstreetcn.com/articles/3783496

**Memory and persistent state.**
Products keep per-agent memory (preferences, role context, summaries of past work) across sessions. Grok Bot's docs still advise having the agent "check the current source instead of relying on memory" before consequential decisions.

The 2026 survey argues that always-on agents are really *persistent-state systems*. Their state includes memories, but also task ledgers, permissions, credentials, commitments and trigger conditions. It finds the research focuses on accumulating state and neglects governing, recovering or deleting it, and proposes six axes to judge each piece of state: authority, scope, mutability, provenance, recoverability, actionability.
Sources: https://docs.x.ai/grok-bot/overview , https://arxiv.org/abs/2606.30306

**Proactivity itself (when to speak up).**
Deciding *when* to help is a learnable skill, separate from doing the task. ProactiveBench (ICLR 2025) has 6,790 events, plus a reward model trained on human accept/reject labels. Their fine-tuned model scored 66.47% F1 on offering help at the right moments.
Source: https://arxiv.org/abs/2410.12361

**Permissions and approval gates.**
Common pattern: proactive reads are allowed, consequential writes are gated. Examples:
- Gemini Spark asks before spending money or sending email.
- Dots runs proactive searches read-only and lets users pick which actions run on their own.
- Grok Bot offers Allow once / Always allow / Deny.
- In the Claude Agent SDK this is built from allowed/disallowed tools, a permission mode, a `canUseTool` callback, and PreToolUse hooks. One deny blocks the call.

Sources: https://gemini.google/overview/agent/spark/ , https://docs.x.ai/grok-bot/security , https://code.claude.com/docs/en/agent-sdk/overview , https://docs.claude.com/en/docs/agent-sdk/permissions

**Automated review in place of humans ("auto review").**
A separate model or rules layer checks risky actions and either lets them proceed, escalates them to a human, or denies them. It covers shell, plugin calls, computer use and delegation. Approving every step by hand doesn't scale when an agent runs 24/7. Grok Bot's docs say it "does not review every side effect."
Source: https://docs.x.ai/grok-bot/security

**Security: the lethal trifecta and credential isolation.**
An agent that has private data, untrusted content, *and* a way to communicate externally can be prompt-injected into exfiltrating data. Always-on agents usually have all three. Mitigations:
- Keep tokens out of the sandbox entirely. Anthropic uses a vault and proxy for OAuth tokens, and git credentials are wired up at sandbox setup so the agent never handles them.
- Label external content as untrusted.

The OWASP Agentic Top 10 (Dec 2025) adds memory/context poisoning (ASI06), cascading failures (ASI08) and rogue agents (ASI10).
Sources: https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/ , https://www.anthropic.com/engineering/managed-agents , https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/

**Cost: idle burn and prompt caching.**
An always-on agent costs money even when it does nothing. Every heartbeat re-sends the system prompt, tools and history. Prompt caching only helps within the cache's time-to-live (TTL). OpenClaw's docs suggest:
- setting the heartbeat just under the cache TTL (for example 55 min for a 1 h TTL) to keep the cache warm;
- pruning the session after it has sat idle past the TTL;
- using `isolatedSession` or `lightContext` heartbeats, which the docs say "dramatically reduces" per-heartbeat tokens.

Products also cap usage: Claude routines get 5, 15 or 25 runs per day by plan, and Grok Bot has its own weekly-reset quota.
Sources: https://docs.openclaw.ai/reference/token-use.md , https://docs.openclaw.ai/gateway/heartbeat , https://claude.com/blog/introducing-routines-in-claude-code , https://x.ai/news/introducing-grok-bot

**Sandboxes / cloud computers.**
The 2026 products give each agent a persistent remote machine, so work continues with your laptop closed. Isolation is done with microVMs (Firecracker). Sandboxes are provisioned lazily: Anthropic says this cut p50 time-to-first-token by about 60%. Treat containers as "cattle," meaning disposable and replaceable.
Sources: https://docs.x.ai/grok-bot/security , https://www.anthropic.com/engineering/managed-agents
