Four rules for new messages

Turns take seconds or minutes, and messages keep arriving while one runs. The lecture's rules for that:1

  1. Drop duplicates. Each message has a unique ID, and the server drops any ID it has already seen. “Unique IDs make retries safe.”
  2. One turn at a time per conversation. Different conversations still run in parallel.
  3. Batch what arrives meanwhile. “3 quick messages → 1 turn.” “Add Maya?” “And Jordan” “Thanks!” become one turn, not three.
  4. The owner skips the line. Your own 1:1 messages and the Stop button “interrupt or stop the turn.” Group chats, Slack, routines and helpers wait at the back.

Steer, collect, interrupt, stop

OpenClaw names four separate behaviours for a message that arrives during a turn. Its per-session lane runs one turn at a time, and every mode starts from that.2

ModeWhat happens to the running turn
collectKeeps running. Queued messages are merged into one follow-up turn after a short quiet window (500 ms debounce by default).
followupKeeps running. Each queued message gets its own later turn.
steer (OpenClaw's default)Keeps running. The new message is injected at the next model boundary. A tool that's already running finishes, but the tool calls it hasn't started yet are skipped.
interrupt / stopAborted. Then the newest message runs.

Steering is the most polished option, but it lives inside the agent loop. Today you're building the layer underneath: the router and queue. Here, the owner's message interrupts, which is the lecture's rule and the simplest correct version. We'll add steering when we build the turn itself.

The subtle one

Aborting a turn does not mean you can start the next one right away. The aborted turn may be in the middle of a tool call or a save. If the next turn starts before it settles, you have two turns on one conversation, which is exactly the race rule 2 exists to prevent. Wait for the aborted turn to finish, then start. This is safe because “every step is saved to the database”:1 an aborted turn leaves a valid record of what it did, up to the point it stopped.

Exercise: build the router

The repo has a starter that behaves like your week-one agent: every wake immediately runs its own turn. Seven tests describe the four rules. Five of them fail.

build/01-router/router.ts        ← edit this
build/01-router/router.test.ts   ← the spec (don't edit)

node --test build/01-router/router.test.ts

The contract:

createRouter(runTurn) → { submit(wake): boolean }   // false = dropped as duplicate
runTurn(conversationId, batch: Wake[], signal: AbortSignal): Promise<void>

Make the tests pass one at a time, in this order: dedupe → serialize → batch → owner skips the line → wait for the aborted turn to settle. It should take about 30–40 lines. Node 24 runs the .ts files directly, with no dependencies.

Hint 1: the data structure

Keep a Set of seen IDs, plus a Map<conversationId, { pending: Wake[], running: AbortController | null, draining: boolean }>.

Hint 2: the loop

A single async drain(conversationId) per conversation: while (pending.length) { const batch = pending.splice(0); await runTurn(...) }. Start it only if that conversation isn't already draining. Wrapping the await in try/catch gives you rule 5 for free.

Hint 3: owner ordering

Insert owner wakes after the last owner wake already in pending (findLastIndex), then call running?.abort().

Free recall, after the exercise

Without looking: why does an owner message abort the turn, while a Slack reply waits? And what would go wrong in a multi-user Slack channel if every human there could abort turns?

The owner is the one person who's directing the work. Their new message usually makes the current turn wrong (“actually, Thursday”), so carrying on wastes money and produces stale output. Other inputs are information that can wait a few seconds for the next batch. If everyone in a busy channel could interrupt, the agent would be aborted over and over and never finish a turn. It's a denial of service carried out by ordinary chat. That's why the rule is tied to who sent the message (source: "owner" and trusted), not to where it was sent.
