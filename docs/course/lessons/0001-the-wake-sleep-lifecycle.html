The wake–sleep lifecycle

Why an always-on agent is mostly not running, and why that's what makes it a viable product.

You've built this loop before:

const messages = [system, userMessage];
while (true) {
  const reply = await llm(messages, { tools });
  messages.push(reply);
  if (!reply.toolCalls.length) { console.log(reply.text); break; }
  for (const call of reply.toolCalls) messages.push(await runTool(call));
}

Lee Robinson opens his Stanford lecture with exactly this loop and one line: “This agent stops when you close the terminal.”1 Everything else in this course is about what you add around this loop so that it keeps working for months.

The counter-intuitive core

“Always-on” doesn't mean a process spinning 24/7. It means any trigger can bring the agent back. The lecture splits the agent into three things with very different lifetimes:2

The lecture's footer line is the whole idea: “When nothing is happening, nothing runs. Everything that matters is saved, so any trigger can bring it back.”2 The same talk puts it more bluntly on its own slide: “Save everything on the server. The virtual machine can then always be rebuilt.”3

Why this is a business decision, not just engineering

Among the lecture's open problems: “Always-on only works if idle agents are nearly free and active ones are cheap.”4 If each of your users had a process running 24/7, cost would grow with the number of users. With the wake–sleep design, cost grows with the number of wake-ups instead. Your pricing has to follow the same unit.

The wake path

So what brings it back? The lecture lists seven trigger sources: you on any app, routines (schedule or webhook), Slack, phone calls or meetings, another agent, background work finishing, and scheduled check-ins. All of them funnel through one path:5

Each box exists for a reason you'll hit in production:

  • Router drops duplicates. Webhooks and clients retry. Without deduplication, one Slack mention can run two turns and send two replies.
  • One queue per conversation, one turn at a time. Two turns running at once on the same conversation would both read and write the same state.
  • “Anything worth saying?” The agent talks to you only through a send tool. Its ordinary text stays private, so ending a turn in silence is a legitimate outcome.6 This is the reverse of your week-one loop, which printed every reply.

It's not just one company's design

The lecture's case study is xAI's Grok Bot. Its docs describe routines that keep running with your laptop closed and that are triggered by a schedule or by Slack and GitHub events.7 Anthropic's Managed Agents arrives at the same split from a different angle: the session lives in an append-only log outside the loop, so a crashed harness can call wake(sessionId) and carry on.8 The open-source OpenClaw wakes differently. It uses a fixed heartbeat (every 30 minutes by default) and replies NO_REPLY (formerly HEARTBEAT_OK) when nothing needs attention.9 Event-driven wake-ups versus heartbeats is the trade-off we'll take on next.

Check yourself

Answer without scrolling up. Getting one wrong is useful: it shows you what to reread.

1. In the lecture's design, which of these exists only while a turn is running?

The process loads state, works, saves each step, and stops after about 2 idle minutes. Rows, memory and routines live in saved state, which is always on.

2. A routine fires at 8:00 and only needs memory and the model, no tools. What does the agent's computer do?

The computer is restored lazily, “when a tool needs it.” A tool-free routine never wakes it, which is a large part of why idle agents can be nearly free.

3. Why does the router drop duplicates before anything is queued?

Networks and webhook senders retry. The lecture gives every message a unique ID so “retries are safe”: the server drops any ID it has already seen.

4. A webhook wakes the agent. It checks the situation and finds nothing new. What should it do?

“Quiet is allowed.” Users only see what goes through the send tool. The lecture lists “when to speak” as an open problem: too many messages are noise.

5. Why does each conversation get its own queue that runs one turn at a time?

Concurrent turns on the same conversation would race on its history and memory. Serializing per conversation removes that race, and different conversations can still run in parallel.

6. Per the lecture, always-on only works as a business if…

From the “Open problems” slide: “idle agents are nearly free and active ones are cheap.” The wake–sleep lifecycle is how you get the first half.

Free recall

A teammate @-mentions your agent in Slack. Write every stage that mention passes through, from arriving to (maybe) reaching a human, and say what each stage protects against.

  1. Trigger: the Slack event arrives and records its source (Slack, not the owner), so the agent knows who asked.
  2. Router: drops it if it's a retry it has already seen, and maps it to the right conversation.
  3. Conversation queue: it waits if a turn is already running there. Several quick messages can be batched into one turn.
  4. Agent process wakes: it loads state from the database and runs model → tools → repeat, saving every step. The computer is restored only if a tool needs it.
  5. Anything worth saying? If yes, it calls the send tool, which routes the message to Slack. If no, it stays quiet.
  6. Sleep: the process stops after about 2 idle minutes. Everything is already saved.
